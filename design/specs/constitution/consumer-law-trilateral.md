## 一、三方关系第一性原理

```
公理 R-1: 商场是唯一的信任锚点。生产者与消费者之间不存在直接信任关系，
          一切信任通过商场的中介与背书建立。

公理 R-2: 生产者对消费者负有间接义务。生产者不直接服务消费者，
          生产者履约的对象是商场，商场再向消费者交付。

公理 R-3: 消费者对生产者不享有直接权利。消费者不能命令生产者生产，
          消费者只能通过商场表达意图，由商场调度生产者。

公理 R-4: 商场对双方负有绝对中立义务。商场不得偏袒任何一方，
          不得利用信息优势谋取私利。

公理 R-5: AICoder是第四方观察者。AICoder不直接参与三方交互，
          但拥有对三方行为的审查、评估、进化建议权。
```

## 二、关系拓扑图

```
                        ┌─────────────────────────┐
                        │      第四方: AICoder      │
                        │    (审查·评估·进化建议)    │
                        │         ↑ 审计流          │
                        └─────────┬───────────────┘
                                  │
                                  ↓
┌──────────────┐      意图流      ┌──────────────┐      产出流      ┌──────────────┐
│              │ ───────────────→ │              │ ───────────────→ │              │
│   消费者     │                  │     商场     │                  │   生产者     │
│ (Consumer)   │ ←─────────────── │    (Mall)    │ ←─────────────── │ (Producer)   │
│              │     交付流       │              │     履约流       │              │
└──────────────┘                  └──────────────┘                  └──────────────┘
       ↑                                  ↑                                  ↑
       │                                  │                                  │
       └──────────────────────────────────┴──────────────────────────────────┘
                                    SHM 总线
                         (消费者区 / 交换区 / 生产者区)
```

**关键约束**:
- 意图流: 单向，消费者 → 商场
- 交付流: 单向，商场 → 消费者
- 履约流: 单向，生产者 → 商场
- 产出流: 单向，商场 → 消费者 (经过交换区中转)
- 审计流: 单向，商场 → AICoder
- **不存在**: 消费者 → 生产者 的直接流
- **不存在**: 生产者 → 消费者 的直接流
- **不存在**: AICoder → 任何一方的控制流 (AICoder只有建议权，无指挥权)

## 四、交易的三方契约模型

一次完整的商场交易，由三份相互关联的契约组成：

### 4.1 契约结构

```
┌─────────────────────────────────────────────────────────────┐
│                    交易契约 bundle                              │
├─────────────────────────────────────────────────────────────┤
│  契约 A: 消费者-商场契约 (C-M Contract)                        │
│  ├─ 消费者提交意图，声明需求与时间承受力                        │
│  ├─ 商场承诺在ETC范围内交付匹配产物                             │
│  └─ 消费者承诺在交付后确认结算，承担ATC                         │
├─────────────────────────────────────────────────────────────┤
│  契约 B: 生产者-商场契约 (P-M Contract)                        │
│  ├─ 生产者承诺按蓝图规格产出数据                                │
│  ├─ 商场承诺提供SHM写入资源与调度优先级                         │
│  └─ 生产者承诺在异常时及时上报，接受商场熔断                      │
├─────────────────────────────────────────────────────────────┤
│  契约 C: 消费者-生产者间接契约 (C-P Indirect Contract)         │
│  ├─ 通过商场背书建立间接关联                                    │
│  ├─ 消费者认可生产者蓝图摘要                                    │
│  └─ 生产者认可消费者意图的合法性                               │
│  ⚠ 注意: C-P契约不直接执行，所有执行通过C-M与P-M契约完成        │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 契约缔结时序

```
T0: 消费者提交意图 → 生成 C-M 契约草案
T1: 商场解析意图，匹配生产者 → 生成 P-M 契约草案
T2: 商场向消费者展示生产者摘要 → 消费者确认/拒绝
T3: 消费者确认 → C-M 契约锁定
T4: 商场向生产者下发调度指令 → P-M 契约锁定
T5: 生产者履约 → 产出物进入交换区
T6: 商场投递产出物至消费者SHM区 → C-M 契约履约
T7: 消费者确认接收 → C-M 契约结算
T8: 商场向生产者记录履约完成 → P-M 契约结算
T9: 审计日志写入，AICoder评估 → 交易闭环
```

## 五、冲突解决机制

### 5.1 冲突类型

| 类型 | 描述 | 典型场景 |
|------|------|----------|
| **需求冲突** | 多个消费者竞争同一生产者的有限产出 | 高频实时数据源被多个监控面板订阅 |
| **产能冲突** | 生产者产能不足，无法满足所有匹配订单 | 复杂算法生产者计算资源饱和 |
| **代价冲突** | 消费者承受力与生产者实际代价不匹配 | 指定型消费遭遇商场拥堵 |
| **质量冲突** | 产出物质量不符合消费者预期 | 数据精度、延迟、完整性不达标 |
| **安全冲突** | 消费者意图与生产者蓝图的安全策略冲突 | 消费者要求外发P3级资产 |

### 5.2 冲突仲裁原则

```
原则 1: 商场中立原则
    商场作为仲裁者，不得偏向消费者或生产者任何一方。
    仲裁依据: 契约条款、历史数据、AICoder评估报告。

原则 2: 时间优先原则
    当多个消费者竞争同一资源时，按以下优先级裁决:
    a) 时效等级更高者优先 (L0 > L1 > L2 > L3)
    b) 同等级时，信用评分更高者优先
    c) 同信用时，先提交意图者优先

原则 3: 代价补偿原则
    当生产者因产能不足无法满足订单时，商场必须:
    a) 向未履约消费者提供替代方案
    b) 向受影响消费者补偿信用积分
    c) 向生产者记录产能缺口，纳入AICoder优化队列

原则 4: 安全压倒原则
    任何涉及安全等级的冲突，安全策略自动获胜。
    消费者不得通过提高时间代价来绕过安全限制。

原则 5: 降级生存原则
    当冲突无法调和时，商场启动降级模式:
    a) 降低非关键消费者的产出频率
    b) 启用备用生产者蓝图
    c) 将部分消费者转入延迟容忍队列
```

## 六、三方信用互联

消费者、生产者、商场共享一个统一的信用空间：

```
信用空间结构:

┌─────────────────────────────────────────┐
│           商场信用总账 (Mall Ledger)      │
├─────────────────────────────────────────┤
│  消费者信用分账 (Consumer Credit)        │
│  ├─ 履约信用 (Fulfillment Credit)        │
│  ├─ 代价信用 (Cost Credit)               │
│  └─ 安全信用 (Security Credit)             │
├─────────────────────────────────────────┤
│  生产者信用分账 (Producer Credit)          │
│  ├─ 履约信用 (Fulfillment Credit)        │
│  ├─ 质量信用 (Quality Credit)              │
│  └─ 稳定信用 (Stability Credit)            │
├─────────────────────────────────────────┤
│  商场自身信用 (Mall Self-Credit)           │
│  ├─ 调度公平性 (Fairness Score)            │
│  ├─ 异常响应速度 (Response Score)          │
│  └─ 审计透明度 (Transparency Score)        │
└─────────────────────────────────────────┘
```

**信用互联规则**:
- 消费者违约 → 消费者信用下降 → 该消费者未来匹配的生产者优先级间接下降
- 生产者违约 → 生产者信用下降 → 订阅该生产者的消费者收到商场预警
- 商场调度失误 → 商场自身信用下降 → AICoder介入分析，提出调度算法进化建议

## 七、AICoder的第四方角色

AICoder在三方关系中扮演**超然的第四方**:

```
AICoder 的权利:
  - 读取全部审计日志与脱敏后的交易数据
  - 对消费者画像、生产者蓝图、商场调度策略进行独立评估
  - 向商场提交进化建议报告 (无强制力)
  - 向创世委员会提交重大缺陷告警

AICoder 的义务:
  - 保持中立，不得为任何一方设计偏向性策略
  - 所有评估报告必须可复现、可审计
  - 不得接触P3级资产的明文内容
  - 不得修改商场运行时的任何状态

AICoder 的禁区:
  - 禁止直接向消费者或生产者发送指令
  - 禁止利用审查权谋取任何形式的"进化优势"
  - 禁止在评估报告中嵌入未声明的偏好参数
```
