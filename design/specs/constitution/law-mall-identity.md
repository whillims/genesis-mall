## 序言：从约束到服务

商场自诞生之日起，便背负着沉重的约束使命——三界隔离、八条铁律、单向性法则、时间契约。这些约束构成了商场的免疫系统，确保生产者、消费者、商场三方的物理隔离与信任锚定。

然而，约束只是手段，服务才是目的。商场的终极使命不是"禁止什么"，而是"实现什么"。本宪章将商场的定位从"重约束"扩展为"约束+服务"双柱模型，在坚守安全底线的同时，为交易提供高带宽路径、透明指标、智能建议、精细调节——使交易更高效、更透明、更可预测。

## 第一章 商场本体论（Mall Ontology）

### 第1条 商场的统一定位

> **商场是实现公平安全交易的场所。**

商场是生产者与消费者之间的唯一中介，通过SHM总线提供数据流通通道，通过掩码匹配确保供需公平，通过时间契约约束交易纪律，通过算力调度优化资源分配。

商场的职责不仅是约束和监管，更是**提供服务**——高带宽路径、交易指标、智能建议——使交易更高效、更透明、更可预测。

### 第4条 商场的权力边界

商场在其主权层（中间层）拥有以下权力：

| 权力 | 范围 | 禁止越界 |
|------|------|----------|
| **调度权** | 算力分配、任务路由、产出速率调节 | 不得干预消费者的意图表达 |
| **编译进化权** | AICoder调用、授权文件管理、函数注册 | 不得拥有设计审核权 |
| **监控权** | 全链路观测、指标产出、安全审计 | 不得作为信用惩罚依据（除非明确违规） |
| **建议权** | 基于指标分析发布优化建议 | 不得未经确认修改消费者意图或人类蓝图 |

## 第二章 高带宽交易路径（High-Bandwidth Trade Paths）

### 第5条 路径分级的必要性

不同时效等级的交易对带宽和延迟的需求差异巨大。L0实时控制指令需要微秒级延迟，L3批处理分析可以容忍秒级延迟。将所有交易统一走同一条SHM通道，既浪费资源又无法保障关键交易的时效性。

### 第6条 四等级路径体系

| 路径等级 | 名称 | 时效等级 | 延迟保障 | SHM策略 | 适用场景 |
|----------|------|----------|----------|---------|----------|
| **P0** | 紧急通道 | L0 实时 | ≤ 1ms | 独占SHM段 + 最高闸口优先级 | 闭环控制指令、安全告警 |
| **P1** | 快速通道 | L1 准实时 | ≤ 10ms | 专用SHM段 + 高闸口优先级 | 频谱显示、状态监控 |
| **P2** | 标准通道 | L2 延迟容忍 | ≤ 100ms | 共享SHM段 + 标准闸口 | 数据分析、融合处理 |
| **P3** | 经济通道 | L3 批处理 | 无保障 | 共享SHM段 + 最低优先级 | 日志归档、审计备份 |

### 第7条 路径分配规则

1. **默认映射**: 路径等级由交易的**时效等级（Latency Class）** 自动映射
2. **生产者声明**: 生产者在蓝图中声明产品的默认时效等级
3. **消费者覆盖**: 消费者在意图中可覆盖时效等级请求（只能升级不能降级，需承担更高代价）
4. **资源限制**: P0通道资源有限，商场有权在P0通道拥堵时拒绝低优先级交易

### 第8条 路径与交易结构

路径等级作为交易的元数据字段：

```
Transaction := {
    ProducerID, ConsumerID, DataPayload, TradeType,
    PathLevel,           // 新增：路径等级 P0/P1/P2/P3
    Timestamp, IntegrityHash
}
```

## 第三章 交易指标体系（Trade Metrics System）

### 第9条 指标作为公共信息产品

商场的"观察权"不仅用于安全审计，还应产出结构化的交易指标，为管理者和消费者提供决策依据。指标是商场的"公共信息产品"，以只读形式发布至SHM。

### 第10条 三层指标体系

| 层级 | 指标名称 | 定义 | 发布频率 | 消费者 |
|------|----------|------|----------|--------|
| **宏观** | δ_mall | 全局时间膨胀系数 | 每秒 | 所有角色 |
| **宏观** | throughput_mall | 全局吞吐量（交易/秒） | 每秒 | 管理者 |
| **宏观** | congestion_index | SHM通道利用率 | 每秒 | 所有角色 |
| **中观** | δ_producer | 单个生产者膨胀系数 | 每5秒 | 管理者、消费者 |
| **中观** | queue_depth | 生产者待处理队列长度 | 每5秒 | 管理者 |
| **中观** | mask_hit_rate | 供需匹配成功率 | 每10秒 | 管理者 |
| **微观** | tx_latency | 单交易端到端延迟 | 实时 | 当事消费者 |
| **微观** | shm_bandwidth | 单SHM段带宽利用率 | 每5秒 | 管理者 |

### 第11条 指标存储与访问

- **宏观指标**: `shm://mall/metrics/global`，所有角色只读
- **中观指标**: `shm://mall/metrics/producer/{id}`，管理者和相关消费者只读
- **微观指标**: `shm://mall/metrics/tx/{tx_id}`，仅当事方只读
- 指标数据为**SEALED态只读产品**，不可篡改

## 第四章 主动建议能力（Proactive Advisory）

### 第12条 建议权的法理基础

商场基于交易指标的分析，主动向管理者或消费者提出优化建议。建议权是调度权的自然延伸——商场既然能调度资源，就应当告知调度决策的依据和建议。

**建议权 ≠ 干预权**: 商场提出建议，但建议的执行权归属不同角色。

### 第13条 建议分类与执行权限

| 建议类型 | 触发条件 | 建议内容 | 执行者 | 权限性质 |
|----------|----------|----------|--------|----------|
| **算力再分配** | δ_producer > 1.5 持续30秒 | 为Worker-X分配更多算力 | 商场调度器 | 调度权，直接执行 |
| **产出节流** | shm_bandwidth > 80% 持续10秒 | 降低Worker-Y的产出速度 | 商场调度器 | 调度权，直接执行 |
| **优先级调整** | queue_depth > 阈值 | 提升任务-Z的优先级 | 消费者 | 建议权，需确认 |
| **生产者切换** | δ_producer > 2.0 持续60秒 | 切换至备用生产者 | 消费者 | 建议权，需确认 |
| **蓝图优化** | TCS < 200 持续5分钟 | AICoder审查Worker-W蓝图效率 | AICoder/人类 | 建议权，溢出至人类社会 |
| **通道升级** | tx_latency > L1阈值 | 升级至P0紧急通道 | 消费者 | 建议权，需确认 |

### 第14条 建议的形态

建议以**结构化事件产品**（EVENT类型）发布至SHM：

```python
{
    "suggest_id": "SUG-{timestamp}-{seq}",
    "suggest_type": "throttle_producer",    # 建议类型编码
    "target": "worker_id",                  # 建议对象
    "reason": "trigger_reason_code",        # 触发原因编码
    "evidence": {"metric": value, ...},     # 证据数据
    "action": {"param": "key", "value": v}, # 建议参数
    "authority": "auto_execute",            # auto_execute / consumer_confirm / human_review
    "ttl_ms": 30000                         # 建议有效期
}
```

### 第15条 建议权与干预权的边界

| 商场可以 | 商场不可以 |
|----------|------------|
| 基于调度权直接执行算力分配和产出节流 | 未经确认修改消费者的意图或任务参数 |
| 发布建议事件产品供消费者/人类参考 | 未经人类审核修改Worker的蓝图规格 |
| | 基于建议对任何角色进行惩罚（惩罚必须基于明确的违宪行为） |

## 第五章 产出速度调节（Output Rate Control）

### 第16条 从二元到连续的调度进化

现有的调度是**二元决策**（执行/不执行、分配/不分配），缺乏**连续调节**能力。产出速度调节是在"完全停止"和"全速运行"之间引入精细的速率控制，使商场能够平滑地管理SHM带宽资源。

### 第17条 速率控制参数

| 控制参数 | 定义 | 范围 | 默认值 |
|----------|------|------|--------|
| `output_rate` | 产出速率系数 | [0.0, 1.0] | 1.0（全速） |
| `batch_interval_ms` | 批次最小间隔 | [0, ∞) ms | 0（无限制） |
| `max_products_per_cycle` | 单周期最大产出数 | [1, ∞) | ∞（无限制） |

- `output_rate = 1.0`: 全速运行（默认）
- `output_rate = 0.5`: 半速运行，每两个调度周期执行一个
- `output_rate = 0.0`: 暂停产出（等效于调度暂停，但保留Worker注册）

### 第18条 调节触发条件

| 触发场景 | 调节方向 | 调节幅度 | 恢复条件 |
|----------|----------|----------|----------|
| SHM带宽利用率 > 80% | 降低 | -0.1 / 次 | 带宽 < 60% |
| SHM带宽利用率 > 95% | 大幅降低 | -0.3 / 次 | 带宽 < 50% |
| 消费者ACK延迟 > t₁ × 0.8 | 降低 | -0.2 / 次 | ACK延迟正常 |
| 目标消费者离线 | 暂停 | → 0.0 | 消费者重新上线 |
| SHM带宽利用率 < 40% | 恢复 | +0.1 / 次 | — |
| 紧急任务插入（P0） | 抢占降速 | 非紧急Worker -0.2 | 紧急任务完成 |

### 第19条 调节权限与审计

- **商场调度器**有权调节任何Worker的产出速率（调度权范围内）
- **消费者**有权通过控制交易请求调节其订阅的生产者的产出速率（需商场审批）
- **生产者**无权自行调节速率，但可以在蓝图中声明`max_output_rate`上限
- 速率调节事件记入审计日志，包含调节原因、幅度、执行者
