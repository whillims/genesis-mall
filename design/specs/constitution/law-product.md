# 产品本体论与产品法（Product Ontology & Product Law）

**版本**：v1.0 纲领性文档
**编号**：LAW-PRODUCT-0001
**地位**：商场数据实体的最高定义法，统合交易掩码、SHM矢量空间、三方契约中的碎片化术语
**核心隐喻**：产品是商场的货币——它由生产者铸造，经商场流通，被消费者持有，其成色由掩码保证，其流通由单向性法则约束

## 第一章 产品本体论（Product Ontology）

### 第1条 产品的定义

**产品（Product）** 是商场体系中生产者向消费者传递的**数据实体的唯一合法形态**。其严格定义为：

```
Product := {
    ProductID,          // 产品唯一标识
    ProducerID,         // 生产者身份标识
    ProductType,        // 产品类型编码（RAW/PROCESSED/EVENT/CONTROL）
    ProductSignature,   // 产品特征签名（如 "spectrum.f32.4096"）
    DataPayload,        // 实际数据内容，存储于SHM矢量
    Timestamp,          // 商场原子时戳
    IntegrityHash,      // 数据完整性校验值
    DurabilityFlag,     // 持久性标志（Ephemeral/Durable）
    SHMVectorRef        // 关联的SHM矢量引用
}
```

### 第2条 产品的本质属性

产品具有以下不可分割的本质属性：

| 属性 | 定义 | 法理依据 |
|------|------|----------|
| **实体性** | 产品是独立存在的数据实体，拥有唯一标识和生命周期 | 三方契约 T5-T6 |
| **单向性** | 产品只能从生产者经商场流向消费者，不可逆流 | 交易掩码第2条 |
| **不可变性** | 产品一经封印确认，其内容不可修改、不可回滚、不可删除 | 交易掩码第8-9条 |
| **可追溯性** | 产品的完整流通路径可被商场全链路观测 | 交易掩码第10条 |
| **抽象性** | 产品是语义层概念，不绑定任何特定的物理存储或UI表现形式 | 产品-相-UI三层架构 |

### 第3条 产品的四层切面

产品在不同语境下呈现四个切面，它们是同一事物的不同观察角度：

```
                    ┌─────────────────────────────────┐
                    │         产品 (Product)           │
                    │     商场数据实体的唯一正式名称     │
                    └────────┬────────────────────────┘
                             │
            ┌────────────────┼────────────────┐
            │                │                │
            ▼                ▼                ▼
    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
    │  语义层切面   │ │  交易层切面   │ │  物理层切面   │
    │  Product     │ │  DataPayload │ │  SHM矢量     │
    │  (产品)      │ │  (数据载荷)   │ │  (共享内存)   │
    └──────────────┘ └──────────────┘ └──────────────┘
            │                │                │
            │                │                │
            ▼                ▼                ▼
    产品特征签名      交易结构字段       头-体-尾布局
    product_mask     IntegrityHash    version/checksum
    ProductType      TradeType        dtype/capacity
```

| 切面 | 别名 | 关注点 | 管辖宪章 |
|------|------|--------|----------|
| 语义层 | 产品、产出物、生产数据、产物 | 数据的含义、类型、签名 | 本宪章 |
| 交易层 | DataPayload | 数据在交易中的载体角色 | 交易掩码法则 |
| 物理层 | SHM矢量、输出矢量 | 数据在共享内存中的存储形态 | SHM矢量空间总则 |

### 第4条 产品不是什么

以下概念**不是**产品，必须严格区分：

| 概念 | 与产品的区别 |
|------|-------------|
| **交易 (Transaction)** | 交易是产品流通的**过程**（动词），产品是交易中传递的**实体**（名词） |
| **任务 (Task)** | 任务是产品的**编排容器**，一个任务可包含多个产品的生产与消费 |
| **意图 (Intent)** | 意图是消费者对产品的**需求描述**，产品是需求的**满足物** |
| **蓝图 (Blueprint)** | 蓝图是产品的**设计图纸**，产品是蓝图执行的**产出结果** |
| **SHM矢量** | SHM矢量是产品的**物理存储**，产品是SHM矢量的**语义解释** |

## 第二章 产品生命周期（Product Lifecycle）

### 第5条 产品生命六阶段

产品的完整生命周期由六个阶段组成：

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  铸造     │ → │  提交     │ → │  封印     │ → │  投递     │ → │  结算     │ → │  终结     │
│ (MINT)   │    │ (SUBMIT) │    │ (SEAL)   │    │(DELIVER) │    │ (SETTLE) │    │ (FINISH) │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
     │               │               │               │               │               │
  生产者执行      写入SHM交换区    SHA-256校验     商场路由至       消费者ACK       回收SHM槽位
  产生输出数据    商场记录元数据   冻结为只读      消费者SHM区      或强制确认       归档审计日志
```

### 第6条 各阶段详解

#### 6.1 铸造阶段 (MINT)

- **执行者**：生产者 Worker
- **行为**：生产者执行授权函数，产生输出数据
- **规则**：输出数据必须符合蓝图声明的 `product_spec` 规格与 `OutputMask` 掩码范围
- **违宪**：生产超出掩码范围的数据类型，构成**掩码越界**

#### 6.2 提交阶段 (SUBMIT)

- **执行者**：生产者 Worker → 商场
- **行为**：产品作为交易的一部分，写入商场SHM交换区
- **规则**：
  - 商场分配SHM矢量槽位
  - 商场记录交易元数据（ProducerID, Timestamp, IntegrityHash）
  - 商场验证产品类型与生产者OutputMask的一致性
- **违宪**：绕过商场直接向消费者提交产品，构成**主权背叛**

#### 6.3 封印阶段 (SEAL)

- **执行者**：商场
- **行为**：数据写入完成后，商场对SHM矢量执行封印操作
- **规则**：
  - 计算body数据的SHA-256校验和
  - 状态从ACTIVE冻结为SEALED
  - 封印后禁止任何写入操作
- **法理**：封印是产品获得**不可变性**的时刻，封印前的数据是"草稿"，封印后的数据是"产品"

#### 6.4 投递阶段 (DELIVER)

- **执行者**：商场 → 消费者
- **行为**：商场将封印后的产品路由至匹配的消费者SHM区
- **规则**：
  - 消费者对产品处于**只读状态**
  - 一对多广播时，商场复制数据到多个消费槽位
  - 多对一聚合时，商场按时间戳交错写入，消费者负责解复用
- **违宪**：消费者反向写入生产者的原始数据区，构成**写隔离违规**

#### 6.5 结算阶段 (SETTLE)

- **执行者**：消费者 → 商场
- **行为**：消费者向商场发送消费确认（ACK），或商场在超时后代发强制确认
- **规则**：
  - 确认后交易状态冻结为**历史（Historical）**
  - 瞬时产品：确认后商场可回收SHM槽位
  - 持久产品：确认后保留至任务终结
- **法理**：结算是产品所有权从"商场托管"转移到"消费者持有"的时刻

#### 6.6 终结阶段 (FINISH)

- **执行者**：商场
- **行为**：产品完成其全部使命，进入终态
- **规则**：
  - 瞬时产品：结算后立即回收SHM槽位
  - 持久产品：任务终结后归档，保留审计周期，然后回收
  - 归档期间产品处于ARCHIVED状态，仅允许读取
  - 回收后产品进入VOID状态，从注册表永久注销
- **法理**：终结不可逆。产品一旦VOID，其ProductID从商场宇宙中永久消失

### 第7条 产品状态机

```
                    生产者执行
    [UNBORN] ──────────────────► [MINTED]
    (未铸造)                        (已铸造)
                                     │
                            商场接收提交
                                     ▼
                              [SUBMITTED]
                              (已提交)
                                     │
                            商场封印校验
                                     ▼
                              [SEALED]
                              (已封印)
                                     │
                            商场路由投递
                                     ▼
                              [DELIVERED]
                              (已投递)
                                     │
                          ┌──────────┴──────────┐
                    消费者ACK确认          超时强制确认
                          │                     │
                          ▼                     ▼
                      [SETTLED]            [FORCED]
                      (已结算)             (强制结算)
                          │                     │
                          └──────────┬──────────┘
                                     │
                            任务终结/审计期满
                                     ▼
                              [ARCHIVED]
                              (已归档)
                                     │
                            SHM槽位回收
                                     ▼
                               [VOID]
                               (终结)
```

### 第8条 生命周期铁律

1. **封印不可逆**：产品一旦封印，其内容永远不可修改
2. **结算不可撤**：消费者ACK一旦发送，消费行为不可撤销
3. **终结不可复**：产品一旦VOID，其ProductID永久注销，不可复用
4. **错误向前修正**：若产品数据有误，只能由另一个生产者生成修正产品（补偿交易），原产品保留作为审计痕迹

## 第三章 产品属性体系（Product Attribute System）

### 第9条 产品类型编码

产品按语义分为四种基本类型，由 `ProductType` 字段标识：

| 类型编码 | 名称 | 定义 | 典型场景 | 持久性默认 |
|----------|------|------|----------|------------|
| `RAW` | 原始产品 | 生产者直接采集的未经处理的数据 | 键盘输入、网络包、传感器数据 | 瞬时 |
| `PROCESSED` | 加工产品 | 经一个或多个Worker处理后的衍生数据 | 频谱分析结果、融合判决、控制指令 | 持久 |
| `EVENT` | 事件产品 | 异步通知类数据，不含业务载荷 | 状态变更、异常告警、里程碑 | 瞬时 |
| `CONTROL` | 控制产品 | 携带控制语义的特殊产品 | 暂停、加速、参数调整 | 瞬时 |

### 第10条 产品特征签名

每个产品拥有一个**产品特征签名 (ProductSignature)**，用于意图匹配：

```
格式: {domain}.{dtype}.{size}
示例: spectrum.f32.4096     — 频谱数据，float32，4096点
      keyboard.u8.1         — 键盘输入，uint8，1字节
      feedback.f32.8        — 控制反馈，float32，8元素
```

- 签名由生产者在蓝图授权文件中声明
- 消费者意图中的 `product_signature` 字段必须与签名匹配
- 签名不匹配时，商场匹配引擎拒绝配对

### 第11条 产品掩码

产品掩码 (ProductMask) 是一个位图，描述产品所属的数据类型集合：

```
ProductMask := b₃₁b₃₀...b₁b₀
其中 bᵢ = 1 表示产品属于第 i 类数据语义
```

- 生产者的 `OutputMask` 声明其能产出的产品掩码
- 消费者的 `DemandMask` 声明其愿意接收的产品掩码
- 匹配条件：`DemandMask & OutputMask ≠ 0`

### 第12条 产品持久性

| 持久性 | 标志 | 行为 | 适用场景 |
|--------|------|------|----------|
| **瞬时 (Ephemeral)** | `EPH` | 消费者读取即视为消费，商场可立即回收槽位 | 高频流数据、事件通知 |
| **持久 (Durable)** | `DUR` | 数据保留至任务终结，允许多次读取（不可修改） | 分析数据、验证结果 |

- 持久性由蓝图中的 `TradeDurabilityFlag` 声明
- 消费者可在创建任务时覆盖持久性请求，但生产者有权拒绝不匹配其能力的覆盖

### 第13条 产品所有权

| 阶段 | 所有权归属 | 权限 |
|------|------------|------|
| MINT → SUBMIT | 生产者 | 生产者拥有产品的创建权，但提交后丧失修改权 |
| SUBMIT → SEAL | 商场托管 | 商场拥有产品的存储权、校验权、路由权 |
| SEAL → DELIVER | 商场托管 | 商场拥有产品的投递权，消费者只读访问 |
| DELIVER → SETTLE | 商场托管 | 消费者发送ACK，确认接收 |
| SETTLE → ARCHIVED | 消费者持有 | 消费者拥有产品的使用权，商场保留审计权 |
| ARCHIVED → VOID | 审计系统 | 产品进入公共审计域，最终回收 |

### 第14条 产品元数据

每个产品携带以下不可篡改的元数据：

| 字段 | 类型 | 定义 | 生成者 |
|------|------|------|--------|
| `ProductID` | string | 产品唯一标识 | 商场 |
| `ProducerID` | string | 生产者身份标识 | 生产者（蓝图声明） |
| `ProductType` | enum | RAW/PROCESSED/EVENT/CONTROL | 生产者（蓝图声明） |
| `ProductSignature` | string | 产品特征签名 | 生产者（蓝图声明） |
| `Timestamp` | uint64 | 商场原子时戳 | 商场 |
| `IntegrityHash` | bytes | SHA-256完整性校验值 | 生产者计算，商场+消费者双重核验 |
| `DurabilityFlag` | enum | EPH/DUR | 生产者声明，消费者可覆盖请求 |
| `SHMVectorRef` | string | 关联的SHM矢量引用 | 商场 |

## 第四章 产品与相的关系（Product-Phase Relationship）

### 第15条 产品-相-UI三层架构

产品、相、UI构成商场的三层呈现架构，三者严格分离：

```
┌─────────────────────────────────────────────────────────┐
│                    三权分立架构                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐  │
│  │   产品层     │    │    相层      │    │   UI层      │  │
│  │  (Product)  │    │  (Phase)    │    │  (UI)       │  │
│  │             │    │             │    │             │  │
│  │  抽象数据    │───→│ 呈现方式    │───→│ 物理载体    │  │
│  │  生产者域    │    │ 消费者域    │    │ AICoder域   │  │
│  └─────────────┘    └─────────────┘    └─────────────┘  │
│                                                         │
│  产品不绑定相    相不绑定UI    三权分立保障迁移自由       │
└─────────────────────────────────────────────────────────┘
```

### 第16条 三层定义

| 层 | 名称 | 定义 | 所属域 | 职责 |
|----|------|------|--------|------|
| 产品层 | Product | 生产者产生的**抽象数据**，具有类型、签名、掩码等语义属性 | 生产者域 | 定义"数据是什么" |
| 相层 | Phase | 消费者对产品**呈现方式的要求**，描述数据应如何被观测 | 消费者域 | 定义"数据怎么看" |
| UI层 | UI | 将抽象产品表现为**具体界面**的物理载体 | AICoder域 | 定义"数据长什么样" |

### 第17条 产品与相的解耦铁律

1. **产品不知道相的存在**：产品作为抽象数据，不包含任何关于如何呈现的信息。一个产品可以被多个不同的相消费，呈现完全不同的形态。

2. **相不修改产品**：相只定义呈现方式，不改变产品的数据内容。消费者对产品处于只读状态。

3. **一对多映射合法**：一个产品可以被多个相同时消费（一对多广播），每个相独立渲染。

4. **多对一映射合法**：多个产品可以被同一个相聚合消费（多对一聚合），相负责融合呈现。

5. **相的迁移自由**：由于产品与相解耦，消费者可以自由更换相（改变呈现方式），而无需修改产品或生产者。

### 第18条 相的数据绑定

相通过以下机制绑定产品数据：

```
消费者相 (Phase)
  │
  ├── 产品引用: product_signature = "spectrum.f32.4096"
  ├── SHM绑定: 只读映射到商场分配的SHM矢量段
  ├── 呈现参数: 刷新率、颜色映射、坐标范围等（写入独立配置SHM段）
  └── 交互状态: 光标位置、缩放级别等（写入独立状态SHM段）
```

- 相通过 `product_signature` 声明其需要消费的产品类型
- 商场匹配引擎将产品路由到相的SHM区
- 相的呈现参数和交互状态写入**独立的SHM段**，不污染产品数据

### 第19条 UI的独立性

UI是相的物理实现，遵循以下独立性原则：

| 原则 | 内容 |
|------|------|
| 技术无关 | 产品不关心UI是Console、Web、GUI还是嵌入式屏幕 |
| 可替换 | 同一个相可以有多个UI实现（如暗色/亮色主题） |
| AICoder责任 | UI的实现是AICoder域的职责，生产者和消费者不参与 |
| 数据只读 | UI只能读取产品数据，任何用户交互产生的状态写入独立SHM段 |

## 第五章 产品安全法则

### 第20条 产品完整性保障

| 保障层 | 机制 | 法理依据 |
|--------|------|----------|
| 生产者层 | 生产者计算IntegrityHash（SHA-256） | 交易掩码第1条 |
| 商场层 | 商场封印时二次校验，写入checksum | SHM矢量空间第10.1节 |
| 消费者层 | 消费者读取时核验IntegrityHash | 交易掩码第1条 |
| 审计层 | 全链路数据血统（Data Lineage）记录 | 交易掩码第10条 |

### 第21条 产品污染处置

产品数据在以下情况下被视为**污染**：

| 污染类型 | 定义 | 处置 |
|----------|------|------|
| 完整性污染 | IntegrityHash校验失败 | 标记CORRUPTED，触发SHM三级熔断 |
| 掩码越界 | 产品类型不在OutputMask范围内 | 拒绝提交，记录生产者信用扣减 |
| 类型伪造 | ProductType与实际数据不匹配 | 拒绝封印，启动安全审计 |
| 越权访问 | 未授权实体读取产品数据 | 冻结访问权限，记录审计日志 |

### 第22条 产品加密

- 产品数据默认以明文存储于SHM
- 生产者可在蓝图中声明加密方案，由AICoder审查
- 加密产品的 `product_signature` 需标注加密标识
- 商场不窥探DataPayload的语义内容（除非启动安全审计）
