## 一、总则序言

> **"蓝图是意图的载体，格式是契约的形体。缺一章则意图不明，错一项则契约失效。"**

蓝图是生产者域向商场域表达函数设计意图的**唯一合法文件**。蓝图不包含可编译代码，不包含二进制对象，不包含外部链接——蓝图是**意图的声明**，不是**实现的提交**。

本总则将散落于《创世纪总纲》第3-5条、各协议文档、实际蓝图文件中的格式规范，统一收编为独立宪法，作为所有蓝图编写、审查、索引的最高格式依据。

---

## 二、根本原则

### 原则一：格式即契约

蓝图的结构、字段、命名必须严格遵守本总则。任何**缺章、缺项、格式偏离**，AICoder有权不予受理。

### 原则二：意图而非实现

蓝图描述的是**函数应该做什么**（what），而不是**函数怎么做**（how）。允许包含算法行为级描述（伪代码、自然语言、数学公式），禁止包含可直接编译的源代码。

### 原则三：生产者永久责任

生产者对蓝图中声明的前置条件、后置条件、资源约束、安全自证承担**永久责任**。若商场发现蓝图描述与授权代码语义严重背离，商场有权吊销该函数句柄并追溯生产者信用。

### 原则四：三界流通的唯一入口

蓝图是生产者域→AICoder域的**唯一合法流通物**。AICoder审查蓝图后生成授权文件，授权文件是AICoder域→商场域的唯一合法流通物。蓝图本身**永远不得直接进入商场域**。

## 三、蓝图结构宪法

### 3.1 标准八节结构

蓝图必须包含以下八个章节，顺序固定，编号连续，不得跳号：

```
# 蓝图文档（定稿版）：{蓝图ID} -- {蓝图名称}

## 1. 蓝图元数据
## 2. 功能概述
## 3. 函数设计（函数级，无类）
## 4. 行为契约
## 5. 测试场景（验收标准）
## 6. 依赖与资源声明
## 7. 安全与隔离铁律
## 8. 授权文件生成要求（致外置AICoder）
```

### 3.2 章节独立性

每个章节必须**自成一体、可独立审查**。AICoder七维审查中的每一维应能定位到具体章节进行验证。

### 3.3 禁止OOP

所有设计为**纯函数级**，禁止类定义、继承、装饰器封装、self引用。这是总纲第15条三大零原则在蓝图层面的体现。

## 四、蓝图元数据规范

### 4.1 必填元数据表

第1节必须以表格形式呈现以下字段：

| 字段 | 格式要求 | 示例 |
|------|----------|------|
| 蓝图ID | `BP-{四位编号}` 或 `BP-{四位编号}-{后缀}` | `BP-0001-ORIGIN` |
| 蓝图名称 | 人类可读的功能名称 | 键盘生产者 |
| 生产者 | 生产者唯一身份标识 | `Genesis-Worker-001` |
| 提交时间 | 日期 `YYYY-MM-DD` | `2026-05-10` |
| 版本 | 语义化版本号 `{主}.{次}.{修订}` | `2.0.0` |
| 目标语言 | 编程语言 | C / Python / Verilog / JavaScript |
| 复杂度等级 | 商场承载评估等级 | `Level-0`（创世纪验证级） |
| 设计范式 | 固定声明 | `纯函数级，禁止OOP封装` |

### 4.2 元数据唯一性

- **蓝图ID全局唯一**：不得与索引中已有ID重复
- **生产者ID全局唯一**：同一生产者的不同蓝图通过蓝图ID区分
- **版本号递增**：同一蓝图ID的版本号必须递增

## 五、功能概述规范

### 5.1 必填内容

第2节必须包含：

| 内容项 | 说明 |
|--------|------|
| 功能描述 | 对函数行为的自然语言描述，清晰界定输入→处理→输出 |
| 数据来源 | 固定声明数据来源（如 `keyboard`、`shm_vector`、`network_stream`） |
| 数据去向 | 声明数据输出目标（如 `stdout`、`shm_vector`、`callback_publish`） |

### 5.2 来源锁定原则

若函数的数据来源不可配置为其他值，必须在功能概述中显式声明**来源锁定**。来源锁定意味着该函数只能处理特定来源的数据，商场调度器据此决定路由策略。

## 六、函数设计规范

### 6.1 主函数签名（第3.1节）

必须提供完整的函数签名，包含：
- 函数名（符合商场命名宪章）
- 所有参数及其类型注解
- 返回值类型
- 算法复杂度声明

```python
def function_name(
    param_a: str,
    param_b: dict,
    config: dict = None
) -> dict:
    """
    [复杂度]: O(n)
    [安全等级]: READ_ONLY_SHM
    """
```

### 6.2 参数规格表（第3.2节）

每个参数必须以表格形式声明：

| 参数名 | 类型 | 必填 | 约束条件 | 说明 |
|--------|------|------|----------|------|
| `param_a` | `str` | 是 | 长度 <= 1024 | 输入数据 |
| `param_b` | `dict` | 是 | 非空 | 配置字典 |

### 6.3 数据来源定义（第3.3节）

若函数从SHM矢量读取数据，必须声明：
- 矢量域（vec/hb/bp/auth/bus）
- 数据类型（bytes/int32/float64/json）
- 预期数据规模

### 6.4 返回值规格（第3.4节）

返回值必须为dict结构，完整定义所有字段：

```python
{
    "status": str,        # "ok" / "error"
    "displayed": str,     # 控制台输出内容
    "timestamp": float,   # 操作时间戳
    "source": str,        # 数据来源标识
    "metadata": dict,     # 附加元数据
    "error": str          # 错误信息（仅status="error"时）
}
```

## 七、行为契约规范

### 7.1 前置条件（第4.1节）

输入校验规则列表，每条对应一个错误码：

| 编号 | 前置条件 | 违反时错误码 | 返回status |
|------|----------|-------------|------------|
| PRE-001 | param_a 长度 <= 1024 | `ERR_INPUT_TOO_LONG` | `error` |
| PRE-002 | param_b 非空 | `ERR_EMPTY_CONFIG` | `error` |

### 7.2 后置条件（第4.2节）

返回值约束列表：

| 编号 | 后置条件 | 说明 |
|------|----------|------|
| POST-001 | status 必须为 "ok" 或 "error" | 不允许其他值 |
| POST-002 | displayed 长度 <= 4096 | 防止输出爆炸 |

### 7.3 不变量（第4.3节）

函数执行过程中**永远不得违反**的约束：

- 零全局状态：不读写任何全局变量
- 零堆分配：不使用 malloc/free/new/delete
- 零系统调用：不进行文件IO、网络IO、进程管理
- 零副作用：不修改输入参数，不产生外部可观察效果（除返回值和SHM写入）
- 确定性：相同输入必得相同输出

### 7.4 错误契约表（第4.5节）

完整的错误码映射：

| 错误码 | 触发条件 | 返回status | 返回displayed | 返回error |
|--------|----------|------------|---------------|-----------|
| `ERR_INPUT_TOO_LONG` | 输入超长 | `error` | `""` | 错误描述 |
| `ERR_EMPTY_CONFIG` | 配置为空 | `error` | `""` | 错误描述 |
| `ERR_PROCESSING_FAILED` | 处理异常 | `error` | `""` | 异常信息 |

| TC-004 | 性能 | 大规模输入 | 默认配置 | 时间/空间约束 |

### 8.2 四类覆盖要求

| 类别 | 定义 | 最低要求 |
|------|------|----------|
| **正常路径** | 符合前置条件的标准输入 | 至少3个用例 |
| **边界路径** | 前置条件的临界值 | 至少2个用例 |
| **异常路径** | 违反前置条件的输入 | 至少2个用例 |
| **性能路径** | 大规模/高频次输入 | 至少1个用例 |

### 8.3 input_builder机制

JSON无法直接表达的特殊输入，使用声明式构造器：

| 构造器 | 用途 | 示例 |
|--------|------|------|
| `repeat` | 重复单字符 | `{"type":"repeat","char":"x","count":1025}` |
| `repeat_text` | 重复文本 | `{"type":"repeat_text","text":"测试","count":50}` |
| `whitespace` | 空白字符 | `{"type":"whitespace","value":"   \n\t  "}` |
| `null_byte` | 空字节 | `{"type":"null_byte","base":"testend","position":4}` |

## 十四、蓝图版本管理

### 14.1 语义化版本号

采用 `{主版本}.{次版本}.{修订号}` 格式：

| 版本段 | 递增条件 | 示例 |
|--------|----------|------|
| 主版本 | 接口签名变更（不向后兼容） | 1.0.0 → 2.0.0 |
| 次版本 | 新增功能（向后兼容） | 1.0.0 → 1.1.0 |
| 修订号 | Bug修复 | 1.0.0 → 1.0.1 |

### 14.2 版本更新规则

- 新授权文件可替换旧版本（同 `blueprint_id`）
- 商场执行二次校验：检查 `blueprint_id` 是否已存在
- 旧版本函数句柄被**吊销**，新版本重新注册
- `auth_version` 必须匹配商场当前版本（当前为 `"1.0"`）

### 14.3 版本兼容性判定

| 变更类型 | 兼容性 | 商场处理 |
|----------|--------|----------|
| 仅修订号递增 | 完全兼容 | 无缝替换 |
| 次版本递增 | 向后兼容 | 无缝替换 |
| 主版本递增 | 不兼容 | 旧版本标记废弃，渐进替换 |

## 十八、蓝图生命周期与状态机

### 18.1 蓝图状态定义

| 状态 | 值 | 含义 |
|------|-----|------|
| `SUBMITTED` | 0x01 | 生产者已提交，等待AICoder受理 |
| `AUDITING` | 0x02 | AICoder正在执行七维审查 |
| `APPROVED` | 0x04 | 七维审查通过，进入代码精化 |
| `DESIGNING` | 0x08 | AICoder正在精化代码 |
| `DEPLOYED` | 0x80 | 授权文件已生成，函数已注册到商场 |
| `REJECTED` | 0xFF | 审查失败，蓝图被驳回 |

### 18.2 合法状态转换

```
[SUBMITTED] ──► [AUDITING] ──► [APPROVED] ──► [DESIGNING] ──► [DEPLOYED]
                   │               │
                   └──► [REJECTED] ◄┘
```

### 18.3 驳回与重提

- 蓝图被驳回后，生产者可修正后重新提交
- 语义歧义最多发回澄清**3轮**，超过则永久驳回
- OOP检测累计**3次**，永久吊销生产者资格
