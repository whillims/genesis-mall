# 商场概念定位分析报告

> **版本**: v1.0 分析报告
> **日期**: 2026-05-12
> **目的**: 梳理商场概念的现有定义碎片，识别差距，设计四项新增能力

---

## 一、任务理解

**目标**: 为"商场"确立统一的概念定位——**商场是实现公平安全交易的场所**，并在此基础上设计四项新增能力：高带宽交易路径、交易指标体系、主动建议能力、产出速度调节。

**约束**: 新增能力必须与现有宪章体系（八条铁律、三界隔离、函数范式、交易掩码、时间契约、产品法等）兼容，不得违背任何上位法。

## 三、差距分析

### 3.1 能力矩阵对比

| 能力域 | 现有定义 | 用户期望 | 差距 |
|--------|----------|----------|------|
| **公平交易** | 三方契约模型、时间契约、掩码匹配 | 商场是实现公平安全交易的场所 | 缺乏"交易场所"的统一定位声明 |
| **高带宽路径** | ❌ 不存在。所有交易统一走SHM，无带宽分级 | 商场应提供高带宽的交易路径 | 完全空白 |
| **交易指标** | 仅有时间膨胀系数δ_mall（宏观拥堵指数） | 商场应提供交易相关指标，为决策提供依据 | 严重不足 |
| **主动建议** | ❌ 不存在。商场仅有"观察权"（宪法总纲6.1节） | 商场应主动提出建议（降速/加算力等） | 完全空白，且与现有"观察权非干预权"存在张力 |
| **产出速度调节** | ❌ 不存在。仅有二元调度（执行/不执行） | 商场应能调节Worker产出速度 | 完全空白 |
| **算力分配** | ✅ 已有丰富定义（算力法条、进程池、动态评估） | 为Worker提供更多算力 | 已有基础，需扩展为建议能力的一部分 |

### 3.2 关键张力分析

**最大张力**: 商场宪法总纲第6.1节定义"商场监控是观察权，不是干预权"，而用户要求商场具备"主动建议能力"（如降低Worker产出速度、分配更多算力）。

**解决思路**: 建议权 ≠ 干预权。商场提出建议，但建议的执行权归属不同角色：

| 建议类型 | 建议者 | 执行者 | 性质 |
|----------|--------|--------|------|
| 降低Worker产出速度 | 商场 | 商场调度器 | 调度权范围内，合法 |
| 为Worker分配更多算力 | 商场 | 商场调度器 | 调度权范围内，合法 |
| 调整任务优先级 | 商场 | 消费者（确认后执行） | 建议权，需消费者确认 |
| 调整蓝图规格 | 商场/AICoder | 人类（审核后执行） | 建议权，溢出至人类社会 |

**结论**: 商场在其调度权范围内可以直接执行资源调节建议；超出调度权的建议以"推荐"形式提交给消费者或人类决策。

## 四、商场统一概念定位设计

### 4.1 核心定位声明（建议）

> **商场是实现公平安全交易的场所。**
>
> 商场是生产者与消费者之间的唯一中介，通过SHM总线提供数据流通通道，通过掩码匹配确保供需公平，通过时间契约约束交易纪律，通过算力调度优化资源分配。商场的职责不仅是约束和监管，更是**提供服务**——高带宽路径、交易指标、智能建议——使交易更高效、更透明、更可预测。

### 4.2 商场职责模型（修订）

将商场的职责从"重约束"扩展为"约束+服务"双柱模型：

```
                    ┌─────────────────────────────────────┐
                    │            商场 (Mall)              │
                    │    公平安全交易的实现场所              │
                    └──────────┬──────────────────────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
              ▼                                 ▼
    ┌──────────────────┐            ┌──────────────────┐
    │    约束柱          │            │    服务柱          │
    │  (Guard Rails)    │            │  (Services)       │
    │                   │            │                   │
    │ · 三界隔离        │            │ · 高带宽交易路径    │
    │ · 单向性法则      │            │ · 交易指标体系      │
    │ · 掩码匹配        │            │ · 主动建议能力      │
    │ · 时间契约        │            │ · 产出速度调节      │
    │ · 安全监控        │            │ · 算力动态分配      │
    │ · 审计追溯        │            │ · 拥堵预测          │
    └──────────────────┘            └──────────────────┘
```

### 4.3 与现有五重定位的关系

| 现有定位 | 与"交易场所"的关系 |
|----------|-------------------|
| 文明操作系统 | 交易场所是文明操作系统的**核心功能定位**，愿景不变，定位更聚焦 |
| 技术宪法 + 物流通道 | 物流通道是交易场所的**物理基础**，宪法是交易场所的**规则基础** |
| 授权文件执行引擎 | 执行引擎是交易场所的**安全准入机制** |
| 供需匹配平台 | 供需匹配是交易场所的**核心服务** |
| 分布式算力调度系统 | 算力调度是交易场所的**资源保障** |

## 五、四项新增能力设计

### 5.1 高带宽交易路径

#### 5.1.1 设计理念

不同时效等级的交易对带宽和延迟的需求差异巨大。L0实时控制指令需要微秒级延迟，L3批处理分析可以容忍秒级延迟。将所有交易统一走同一条SHM通道，既浪费资源又无法保障关键交易的时效性。

#### 5.1.2 路径分级设计

| 路径等级 | 名称 | 时效等级 | 延迟保障 | SHM策略 | 适用场景 |
|----------|------|----------|----------|---------|----------|
| **P0** | 紧急通道 | L0 实时 | ≤ 1ms | 独占SHM段 + 最高闸口优先级 | 闭环控制指令、安全告警 |
| **P1** | 快速通道 | L1 准实时 | ≤ 10ms | 专用SHM段 + 高闸口优先级 | 频谱显示、状态监控 |
| **P2** | 标准通道 | L2 延迟容忍 | ≤ 100ms | 共享SHM段 + 标准闸口 | 数据分析、融合处理 |
| **P3** | 经济通道 | L3 批处理 | 无保障 | 共享SHM段 + 最低优先级 | 日志归档、审计备份 |

#### 5.1.3 路径分配规则

- 路径等级由交易的**时效等级（Latency Class）** 自动映射
- 生产者在蓝图中声明产品的默认时效等级
- 消费者在意图中可覆盖时效等级请求（但只能升级不能降级，且需承担更高代价）
- P0通道资源有限，商场有权在P0通道拥堵时拒绝低优先级交易

#### 5.1.4 与现有宪章的兼容性

| 现有宪章 | 兼容性分析 |
|----------|------------|
| SHM矢量空间总则 | 兼容。路径分级是SHM段的**调度策略**，不改变SHM的物理结构。P0/P1使用独立SHM段，P2/P3共享SHM段 |
| 交易掩码法则 | 兼容。掩码匹配在路径分配之前执行，路径分配是匹配后的**路由优化** |
| 时间契约纲领 | 兼容。路径等级影响t_actual的分布，但不改变t₀和t₁的定义。P0通道的拥堵溢价系数更低 |

### 5.2 交易指标体系

#### 5.2.1 设计理念

商场的"观察权"不应仅用于安全审计，还应产出结构化的交易指标，为管理者和消费者提供决策依据。指标是商场的"公共信息产品"。

#### 5.2.2 指标分层设计

| 层级 | 指标名称 | 定义 | 计算方式 | 发布频率 | 消费者 |
|------|----------|------|----------|----------|--------|
| **宏观** | δ_mall（全局膨胀系数） | 全商场平均时间膨胀系数 | Σ(t_actual/t₀) / N | 每秒 | 所有角色 |
| **宏观** | throughput_mall（全局吞吐量） | 单位时间完成的交易数 | count(settled_tx) / Δt | 每秒 | 管理者 |
| **宏观** | congestion_index（拥堵指数） | SHM通道利用率 | Σ(occupied_shm) / Σ(total_shm) | 每秒 | 所有角色 |
| **中观** | δ_producer（生产者膨胀系数） | 单个生产者的平均时间膨胀 | Σ(t_actual/t₀) / N per producer | 每5秒 | 管理者、消费者 |
| **中观** | queue_depth（队列深度） | 生产者待处理交易队列长度 | len(pending_tx_queue) per producer | 每5秒 | 管理者 |
| **中观** | mask_hit_rate（掩码命中率） | 供需匹配成功率 | count(matched) / count(total_intent) | 每10秒 | 管理者 |
| **微观** | tx_latency（单交易延迟） | 单笔交易的端到端延迟 | t_settled - t_created per tx | 实时 | 消费者（仅自己的交易） |
| **微观** | shm_bandwidth（SHM带宽利用率） | 单个SHM段的读写带宽 | bytes_rw / Δt per shm_segment | 每5秒 | 管理者 |

#### 5.2.3 指标访问规则

- **宏观指标**: 所有角色可读，写入公共SHM段 `shm://mall/metrics/global`
- **中观指标**: 管理者和相关消费者可读，写入 `shm://mall/metrics/producer/{id}`
- **微观指标**: 仅交易当事方可读，写入 `shm://mall/metrics/tx/{tx_id}`
- 指标数据本身是**只读产品**（SEALED态），不可篡改

#### 5.2.4 与现有宪章的兼容性

| 现有宪章 | 兼容性分析 |
|----------|------------|
| 时间契约纲领 | **增强**。δ_mall已在时间契约中定义，指标体系将其扩展为完整的分层指标 |
| 商场监控权边界 | **扩展**。监控权从"安全审计"扩展到"指标产出"，但保持"不干预"原则 |
| SHM矢量空间总则 | 兼容。指标存储于独立SHM段（`metrics`域），遵循SHM宪法 |

### 5.3 主动建议能力

#### 5.3.1 设计理念

商场基于交易指标的分析，主动向管理者或消费者提出优化建议。建议权是调度权的自然延伸——商场既然能调度资源，就应当告知调度决策的依据和建议。

#### 5.3.2 建议分类与执行权限

| 建议类型 | 触发条件 | 建议内容 | 执行者 | 权限性质 |
|----------|----------|----------|--------|----------|
| **算力再分配** | δ_producer > 1.5 持续30秒 | "建议为Worker-X分配更多算力" | 商场调度器 | 调度权，可直接执行 |
| **产出节流** | shm_bandwidth > 80% 持续10秒 | "建议降低Worker-Y的产出速度" | 商场调度器 | 调度权，可直接执行 |
| **优先级调整** | queue_depth > 阈值 | "建议提升任务-Z的优先级" | 消费者 | 建议权，需消费者确认 |
| **生产者切换** | δ_producer > 2.0 持续60秒 | "建议将任务切换至备用生产者" | 消费者 | 建议权，需消费者确认 |
| **蓝图优化** | TCS < 200 持续5分钟 | "建议AICoder审查Worker-W的蓝图效率" | AICoder/人类 | 建议权，溢出至人类社会 |
| **通道升级** | tx_latency > L1阈值 | "建议将交易升级至P0紧急通道" | 消费者 | 建议权，需消费者确认 |

#### 5.3.3 建议的形态

建议以**结构化事件产品**（EVENT类型）发布至SHM：

```python
{
    "suggest_id": "SUG-20260512-001",
    "suggest_type": "throttle_producer",    # 建议类型编码
    "target": "worker_network_rx",          # 建议对象
    "reason": "shm_bandwidth_exceeded",     # 触发原因编码
    "evidence": {"shm_bandwidth": 0.87, "duration_ms": 10000},
    "action": {"param": "output_rate", "value": 0.5},  # 建议参数
    "authority": "auto_execute",            # auto_execute / consumer_confirm / human_review
    "ttl": 30000                            # 建议有效期（毫秒）
}
```

#### 5.3.4 建议权与干预权的边界

| 边界 | 说明 |
|------|------|
| 商场**可以** | 基于调度权直接执行算力分配和产出节流 |
| 商场**可以** | 发布建议事件产品，供消费者/人类参考 |
| 商场**不可以** | 未经确认修改消费者的意图或任务参数 |
| 商场**不可以** | 未经人类审核修改Worker的蓝图规格 |
| 商场**不可以** | 基于建议对任何角色进行惩罚（惩罚必须基于明确的违宪行为） |

#### 5.3.5 与现有宪章的兼容性

| 现有宪章 | 兼容性分析 |
|----------|------------|
| 商场监控权边界（6.1节） | **需修订**。原文"监控是观察权不是干预权"需扩展为"监控是观察权，建议权是调度权的自然延伸，干预权仍被禁止" |
| 三方关系总则 | 兼容。建议通过SHM事件产品发布，遵循单向性法则 |
| 时间契约纲领 | 兼容。建议的触发条件基于时间膨胀系数等已有指标 |

### 5.4 产出速度调节

#### 5.4.1 设计理念

现有的调度是**二元决策**（执行/不执行、分配/不分配），缺乏**连续调节**能力。产出速度调节是在"完全停止"和"全速运行"之间引入精细的速率控制，使商场能够平滑地管理SHM带宽资源。

#### 5.4.2 速率控制模型

| 控制参数 | 定义 | 范围 | 默认值 |
|----------|------|------|--------|
| `output_rate` | 产出速率系数 | [0.0, 1.0] | 1.0（全速） |
| `batch_interval_ms` | 批次最小间隔 | [0, ∞) ms | 0（无限制） |
| `max_products_per_cycle` | 单调度周期最大产出数 | [1, ∞) | ∞（无限制） |

- `output_rate = 1.0`: 全速运行（默认）
- `output_rate = 0.5`: 半速运行，每两个调度周期执行一个
- `output_rate = 0.0`: 暂停产出（等效于调度暂停，但保留Worker注册）

#### 5.4.3 调节触发条件

| 触发场景 | 调节方向 | 调节幅度 | 恢复条件 |
|----------|----------|----------|----------|
| SHM带宽利用率 > 80% | 降低 | -0.1 / 次 | 带宽 < 60% |
| SHM带宽利用率 > 95% | 大幅降低 | -0.3 / 次 | 带宽 < 50% |
| 消费者ACK延迟 > t₁ × 0.8 | 降低 | -0.2 / 次 | ACK延迟恢复正常 |
| 目标消费者离线 | 暂停 | → 0.0 | 消费者重新上线 |
| SHM带宽利用率 < 40% | 恢复 | +0.1 / 次 | — |
| 紧急任务插入（P0） | 抢占降速 | 非紧急Worker -0.2 | 紧急任务完成 |

#### 5.4.4 调节权限

- **商场调度器**有权调节任何Worker的产出速率（调度权范围内）
- **消费者**有权通过控制交易请求调节其订阅的生产者的产出速率（需商场审批）
- **生产者**无权自行调节速率，但可以在蓝图中声明`max_output_rate`上限
- 速率调节事件记入审计日志，包含调节原因、幅度、执行者

#### 5.4.5 与现有宪章的兼容性

| 现有宪章 | 兼容性分析 |
|----------|------------|
| 商场主权层（宪法总纲2.1节） | **增强**。调度权从"分配/不分配"扩展为"连续速率控制"，是调度权的自然细化 |
| Worker主权层 | 兼容。Worker仍只拥有执行权，速率由商场调度器控制，Worker不拥有速率决定权 |
| 交易掩码法则 | 兼容。速率调节影响交易的**频率**，不影响交易的**单向性**和**掩码匹配** |
| 时间契约纲领 | **需协调**。速率降低可能导致t_actual增加，需在时间契约中增加"速率调节免责"条款 |
